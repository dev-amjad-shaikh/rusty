Both actions use the real time-travel API: Fork calls POST /threads/{id}/fork with the selected checkpoint_id (history is copied up to that checkpoint into a new thread); Replay & run starts a background run whose payload carries "checkpoint": {"checkpoint_id": …}, so the executor replays from that checkpoint. On an older server that 404s either call, the Studio falls back to its client-side composition (state write + plain run) and says so in the toast.
